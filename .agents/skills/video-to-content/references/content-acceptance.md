# Content 验收与失败恢复

在准备把 Transcript 交给任意载体，或遇到“文章太短、细节消失、截图不见了”的结果时读取本页。
这页描述的是完成合同，不是另一种文风模板。

## 不要把整条链路当成一个布尔值

每一层都有自己的完成证据，后一层不能替前一层背书：

| 层级 | 证明什么 | 不能证明什么 |
| --- | --- | --- |
| Evidence | 来源可取得，平台字幕、OCR、ASR、封面和帧等观察已持久化 | 哪份证据最能代表原意 |
| Transcript | Agent 已选择、校正并说明不确定性的规范字幕 | 文章已经完成书面化 |
| Content | 来源忠实的可读成稿、章节映射和视觉计划通过验证 | 微信已经保存 |
| Handoff | 已把经过验证的包放入明确的可见编辑器 | 草稿在刷新后仍存在 |
| Draft Receipt | 同一草稿经刷新回读，状态仍为 `published=false` | 可以发布或声明原创 |

渲染成功、正文很长、图片 Artifact 数量正确、保存 Toast、上传结束或出现 `appmsgid`，都只是中间
信号，不能单独当作完成。

## Content 的最低合同

`source_faithful_full` 不是“把字幕换个容器”，也不是把长视频压成摘要。交付前 Agent 必须：

1. 读完完整 Transcript，并建立临时来源地图；
2. 保留原顺序、说话者、专业术语、数字、案例、反例、限制和观点强度；
3. 做真正的书面化：按语义恢复句子，处理口语噪声、转写错误和画面指代；
4. 实际抽查正文开头、中部和结尾，而不是只看标题、摘要或 audit 字段；
5. 为每个实质章节写出 `source_cue_indices -> output_block_indices` 映射，并列出省略；
6. 把有意义的原视频帧插入对应正文位置，`visual_plan.block_index` 必须指向同一 image block；
7. 调用 `content_validate`，只有 `valid=true` 才能进入微信交接。

文章比视频短并不自动错误，但“只剩摘要”“专业细节成片消失”“截图只在 media 列表里、不在正文”
都是 Content 失败，不是可以交给微信编辑器补救的排版问题。长度不是质量指标，完整性和可追溯性才是。

## Agent 与程序各自负责什么

- **Agent 判断**：哪些章节是实质内容；哪些重复可以删；哪里需要回看画面；截图为什么对该段有意义；
  来源语气和专业密度是否被保留。
- **程序验收**：Artifact 哈希和路径、媒体与正文顺序、章节/帧索引是否存在、Profile 契约、
  `raw Transcript passthrough` 高风险形态，以及是否允许进入 handoff。

程序的组合式直贴检查只是安全闸门，不是文风评分器。来源本来就是成熟讲稿时，文字重合可以很高；
不能为了绕过检查而无意义换词，也不能只改 `reviewed_by`、`status` 或 audit 字段。

## 失败后的动作

- 命中 `raw Transcript passthrough`：停在 Content，回到完整 Transcript 重新书面化；不进入微信。
- 内容明显过度压缩：补回来源中的实质章节、案例和限定，再重新做完整审计；不要用“更简洁”解释遗漏。
- 截图缺失或错位：重新做语义选帧并把 image block 放回正文；不要复制相似帧凑最低数量。
- 浏览器读写结果不确定：转到 `wechat-draft` 的恢复清单；先读当前目标和收据，再决定是否重试，绝不直接新建第二篇。
- 无音频、无可读文字或物理证据不足：标记 `unprocessable`，继续下一 Job；不要让用户改变物理条件。
- 技术错误：保留现有 Job、Evidence 和媒体缓存，按限额重试；不要删除目录重跑。
