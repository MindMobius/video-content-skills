# 稍后再看自动化最佳实践加固设计

- 日期：2026-08-17
- 状态：已由用户确认开始实施
- 目标：减少 Agent 的机械操作，强化任务产物路径、状态闭环和最终可观察性，不改变“只保存草稿、绝不发布”的边界。

## 1. 真实问题

13 条视频实跑已经证明主链路可用，但也暴露出三类工程问题：

1. 调用方传入工作区相对路径时，任务代码又按 job 目录拼接一次，导致 `handoff-binding.json` 和部分 fidelity audit 元数据出现重复嵌套路径。
2. 证据完成、规范字幕保存仍依赖 Agent 手工组合多次状态转换和 artifact 绑定，机械步骤多，容易漏记或绑定错路径。
3. 批次结束后缺少一个统一的任务完整性检查，Agent 需要自行拼装“任务是否完成、草稿是否唯一、artifact 是否存在且哈希一致”等结论。

## 2. 方案比较

### 方案 A：重写为常驻编排服务

把扫描、下载、OCR、ASR、写作和浏览器交接全部塞进一个后台服务。

优点：调用入口最少。

缺点：违背仓库的一次性执行边界，浏览器和 GPU 故障会放大成长期运行问题，也会削弱 Agent 对语义判断的控制。

### 方案 B：只修三个已知调用点

分别修复 audit、handoff 和 transition 调用中的相对路径。

优点：改动最小。

缺点：没有统一路径契约，后续新调用点仍可能重复犯错，也不能修复已有任务元数据。

### 方案 C：确定性契约加固，保留 Agent 语义决策

新增统一 job artifact 路径解析、组合式自动化动作、完整性审计和安全元数据修复；Agent 继续负责字幕判断、证据冲突处理和文章写作。

优点：直接解决真实问题，同时符合“程序管状态，Agent 管语义”的项目定位。

**选择方案 C。**

## 3. 设计

### 3.1 统一任务路径契约

新增单一的任务路径模块：

- 绝对路径必须位于 job 目录内；
- 工作区相对路径如果解析后位于 job 目录内，直接使用；
- 普通短相对路径按 job 目录解析；
- job 元数据永远保存 job-relative POSIX 路径；
- 需要读取的 artifact 必须存在，且按记录哈希校验。

这套规则同时供 job transition、内容 audit 和 handoff 使用，禁止各模块自行拼接路径。

### 3.2 组合式自动化动作

新增高层动作以减少 Agent 的机械调用：

- 开始证据处理；
- 校验并绑定已完成的字幕 manifest；
- 保存规范字幕并自动完成 `canonicalizing -> canonical_ready`；
- 规范字幕不可用时自动关闭为 `unprocessable`；
- handoff binding 默认写入 job 根目录，不再要求调用方构造输出路径。

这些动作只合并确定性状态操作，不替代 Agent 的视觉判断、字幕校订和文章创作。

### 3.3 完整性审计与安全修复

新增 job/store 审计：

- artifact 是否位于 job 目录；
- 文件是否存在；
- SHA-256 是否一致；
- completed job 是否存在有效 handoff binding；
- 草稿 `appmsgid` 是否跨任务唯一；
- 是否存在由旧路径拼接错误产生的非规范元数据。

修复模式只允许修改 `job.json` 中的 artifact 相对路径。只有当 job 目录内存在哈希完全一致的规范文件时才修复；不移动、不删除、不覆盖任何原始证据或内容文件。

### 3.4 最终状态摘要

store 级结果输出应包含：

- 各状态数量；
- completed、unprocessable、paused_auth、retry_wait 清单；
- 已绑定草稿及 `appmsgid`；
- 重复草稿 ID；
- artifact 完整性结果；
- 是否达到“本轮处理完成且结果可信”的布尔结论。

用户只需要看最终摘要，内部仍保留逐任务审计细节。

## 4. 不做的事情

- 不新增隐藏 daemon；
- 不自动发布、群发、定时或声明原创；
- 不把字幕冲突处理写成固定多数表决；
- 不增加逐视频审批或质量配置表单；
- 不删除历史重复目录；本轮仅安全修复元数据指向；
- 不改变原始平台字幕、OCR、ASR 和 reviewed artifact。

## 5. 验收标准

1. 工作区相对路径和 job 相对路径都被规范为同一个 job-relative artifact 路径。
2. 旧式重复嵌套元数据能够在哈希一致时被安全修复。
3. Agent 可用单个高层调用完成证据绑定和规范字幕状态闭环。
4. handoff 未提供 output 时稳定写入 `<job>/handoff-binding.json`。
5. store 审计能够发现缺失文件、哈希漂移、重复 appmsgid 和未完成任务。
6. 全部项目回归门通过，且所有发布相关字段仍保持禁止状态。
