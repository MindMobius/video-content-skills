## 测试目的

1. 验证平台写入不会成为 `video-to-content` 的默认步骤；
2. 验证只有 `ready_for_delivery=true` 的文章包才进入公众号后台；
3. 验证正式 HTML 继续保持干净、可审计，同时本地图片可以通过一次性剪贴板运输进入微信；
4. 验证微信接管图片后能被 Agent 从页面状态核实，而不是只相信粘贴动作成功；
5. 验证交接只保存草稿，没有发表，也没有触碰原创、定时、群发或账号管理。

## 为什么普通复制不够

浏览器可以在本地预览中读取 `assets/...`，但系统剪贴板复制富文本时不会自动把这些本地
文件字节送给公众号。直接复制干净 HTML，只会得到文字和路径标记；逐张依靠坐标定位插入
图片又容易受到编辑器结构、滚动和页面改版影响。

因此本轮把正式产物与平台运输拆成两层：

```text
正式产物：干净 HTML + 单行相对路径 + 本地图片
临时运输：剪贴板内的富文本 HTML + data:image/...;base64,...
```

临时层从已审计 HTML 开始，只在内存和剪贴板中按顺序把七个路径标记替换为对应的 Base64
`img`，没有覆盖或另存正式 deliverable，也没有把大段图片数据写入日志。

## 一次粘贴与微信图片接管

整篇临时富文本一次性粘贴到空白正文编辑器。等待微信完成处理后，从页面状态验证：

- 正文可见图片正好是 7 张正文图片；
- 7 张图片的地址都已变为微信托管的 `mmbiz.qpic.cn`；
- `data:` 图片源为 0；
- `file:`、`blob:` 和 `assets/...` 本地图片源为 0；
- 正文中的本地路径文字为 0；
- 文章顺序、来源声明、克制编辑风和正文文字均保留。

这说明 Base64 只承担“把本地图片字节带进编辑器”的一次性运输作用。真正保存到草稿中的
图片已经由微信上传并重写到自己的 CDN，临时地址没有进入最终平台状态。

## 标题、摘要、封面和保存边界

平台元数据按文章审计结果和用户要求处理：

- 标题使用已审计标题；
- 摘要从已审计正文压缩，不引入新事实；
- 通过“从正文选择”把正文第一张原视频封面设为文章封面；
- 作者栏留空；
- 不声明原创；
- 只点击“保存为草稿”，等到页面出现明确已保存状态和稳定文章标识。

本轮没有发表，没有定时，没有群发，也没有修改账号设置。公众号草稿是独立的平台状态，
不能反向把 `audit-001` 的图片交接 warning 改成 `pass`。

## 沉淀出的流程

```text
已审计公众号文章包
-> 用户明确授权草稿交接
-> 检查已登录编辑器与目标正文状态
-> 临时构造含图片字节的 text/html 剪贴板载荷
-> 整篇一次粘贴
-> 验证图片数量与 mmbiz.qpic.cn 接管
-> 填写标题、摘要、封面
-> 只保存草稿
-> 报告平台结果与“未发表”
```

最重要的经验有四点：

1. **Base64 是运输层，不是交付物**：正式 HTML 仍使用单行路径和本地素材，保持可审计、
   可迁移和可人工接手。
2. **平台成功必须读回验证**：粘贴动作成功不等于图片成功，必须核对数量、CDN 地址和本地
   地址清零。
3. **内容状态与平台状态分离**：fidelity audit 证明文章忠实；草稿 receipt 证明浏览器写入
   完成，两者不能互相替代。
4. **Agent 按页面语义操作**：固定的是授权门和后置条件，不是按钮坐标。编辑器变化时读取
   当前页面重新判断；缺少富文本剪贴板能力时回退到人工插图。

这次运行是特定日期、机器、登录会话和微信编辑器版本的观察性案例，不是公共 CI fixture，
也不记录 Cookie、Token、密码、URL token 或账号秘密。
