# BV1KHNC61ExM 实测：硬字幕、ASR 与并发调度

测试日期：2026-08-02（Asia/Shanghai）

视频：[长征十乙成功了，什么叫“从0到1”？](https://www.bilibili.com/video/BV1KHNC61ExM/)，
时长 16 分 08 秒。

## 测试目的

1. 验证 Bilibili 没有平台字幕时能否稳定进入硬字幕 OCR；
2. 比较双尺度 OCR 与 Qwen3-ASR 两路独立证据；
3. 验证 OCR/ASR 并发是否真的缩短整条任务时间；
4. 找出“硬字幕就是正确文稿”这一假设的边界。

## 环境与参数

- GPU：NVIDIA GeForce RTX 5060 Ti，16311 MiB；
- 输入：已下载的同一份本地视频，串行/并行对比均不包含下载时间；
- OCR：VideOCR GPU、固定字幕区域、主宽度 1280、验证宽度 600、每 3 帧采样；
- ASR：Qwen3-ASR-1.7B、Qwen3-ForcedAligner-0.6B、240 秒分块；
- 两次任务都先查询 Bilibili 元数据和平台字幕，再处理本地媒体。

## 结果

| 指标 | 串行基线 | 显式并行 |
| --- | ---: | ---: |
| 整体用时 | 251 秒 | 165 秒 |
| OCR cue | 481 | 481 |
| ASR cue | 143 | 142 |
| 产物 | 15 | 15 |
| 告警 | 0 | 0 |

并行减少 86 秒，约 34.3%。并行任务中，Qwen3-ASR 自报推理 131.3 秒、后端总计
138.5 秒、峰值显存约 10109.9 MiB；GPU OCR 同期完成，没有 OOM 或 stderr。

这是一次主机级可行性验证，不是跨硬件性能保证。ASR cue 数量也出现 143 与 142 的
轻微变化，因此不能用 cue 数相同来定义正确性或确定性。

平台查询结果为 `EMPTY_RESULT`，只证明 Bilibili 没有暴露可用字幕轨，不证明视频
没有硬字幕。随后两路媒体证据都成功生成。

## OCR 的关键反例

双尺度 OCR 的主稿和验证稿高度一致：验证时长覆盖 99.84%，481 个 cue 进入结果，
平均最佳相似度 0.9978。但回看视频帧后发现，部分“错字”本来就烧录在画面里：

- 约 09:17，画面硬字幕是“长江十号”，ASR 与视频主题指向“长征十号”；
- 约 15:56，画面硬字幕是“这次长诗以的成功回收”，ASR、标题和简介共同指向
  “长征十乙”；
- 约 15:36，画面把术语写成拉丁字母 `Tao`，OCR 忠实保留，而 ASR 全片和局部
  重跑分别给出“掏”“套”“涛”等同音候选。

最后一个术语不能靠 OCR 或 ASR 单独定稿。华为官方材料确认正式写法是
[“韬（τ）定律”](https://www.huawei.com/cn/news/2026/5/ieee-iscas-tau-scaling)。

因此需要区分两种准确性：

```text
OCR 是否忠实读取像素
≠
画面中的发布者字幕是否正确表达事实和术语
```

双尺度共识只能提高第一层的稳定性，不能证明第二层。

## 对 Skill 的沉淀

这次测试形成以下默认规则：

1. 平台字幕、OCR、ASR 必须保留为独立证据，不能静默融合；
2. 硬字幕是口播/访谈视频的重要主来源，但仍需允许 ASR 对关键冲突报警；
3. 同音词、专有名词、数字和符号不能由 ASR 单独改写 OCR；
4. 冲突优先读取相邻时间范围、回看源帧和做局部 ASR，避免重跑全片；
5. 仍无法解决时，再查标题、简介、画面标题卡或权威外部来源；
6. `media_execution=auto` 在两路共享 GPU 时保持串行；只有本机 deep doctor 和
   样本验证通过后才显式设为 `parallel`；
7. manifest 必须记录 requested/resolved 调度策略、共享 GPU 判断、每个后端的真实
   开始时间和耗时。

## 限制

- 本次没有人工逐 cue 真值集，因此不报告 OCR 或 ASR 准确率；
- 性能只测一个视频和一台机器，不能代表不同分辨率、字幕样式或显卡；
- 并发验证复用了本地视频，未把网络下载波动混入比较；
- 全片 ASR 使用了已由标题和简介验证过的术语上下文，不能把上下文本身当作证据。
